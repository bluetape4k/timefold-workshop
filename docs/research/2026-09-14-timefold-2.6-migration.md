# Timefold Solver 2.6.0 마이그레이션 근거

## 목적과 근거 범위

이 문서는 Issue #54에서 요구한 Timefold Solver `2.2.0` → `2.6.0`
전환을 버전별 공식 자료와 현재 workshop 의존성 그래프로 고정한다. 2.5와
2.6의 변경만으로 2.3과 2.4의 영향을 추론하지 않도록 각 릴리스의 공식
changelog를 별도로 확인했다.

- 확인일: 2026-09-14 (Asia/Seoul)
- 대상 저장소: `bluetape4k/timefold-workshop`
- 현재 작업 HEAD: `0afdbe9213877e290b8bfec0c8eec47de64dfc5f`

- 중앙 카탈로그: `bluetape4k-dependencies` BOM이 Timefold 버전을 소유하고,
  workshop의 `libs.timefold.solver.*` alias는 versionless로 소비한다.

### 공통 compatibility 판단

Timefold 문서는 `ai.timefold.solver.*.api` 및 `*.config`를 minor/hotfix에서
호환되는 public API로 분류하고, 그 밖의 implementation class는 호환성
보장이 없다고 명시한다. 따라서 이번 작업은 internal implementation class나
`ScoreDirector`에 의존하지 않고 public `SolverManager`, planning annotations,
`SolutionManager.updateShadowVariables`만 사용한다. library integration 문서의
`withFinalBestSolutionEventConsumer`와 immutable problem ID 계약도 lifecycle
테스트의 기준으로 삼는다.

## 현재 catalog와 dependency graph

### 선언 surface

`gradle/libs.versions.toml`에는 다음 alias가 versionless로 선언돼 있다.

```text
timefold-solver-core
timefold-solver-jackson
timefold-solver-spring-boot-starter
```

root `build.gradle.kts`는 `libs.bluetape4k.dependencies`를 dependency-management
BOM으로 import한다. 이전 `e47496a`에는 local `timefold-solver = "2.2.0"`와
`timefold-solver-bom` alias가 있었지만, 현재 catalog에는 local Timefold version
ref가 없다. 중앙 BOM과 checked-out catalog의 책임을 섞지 않는 것이 이번
전환의 고정 결정이다.

### 재현 명령과 결과

다음 명령은 동일한 `:school-timetabling:runtimeClasspath`에 대해 실행했다.

```bash

./gradlew :school-timetabling:dependencyInsight \
  --dependency timefold-solver-core --configuration runtimeClasspath
./gradlew :school-timetabling:dependencyInsight \
  --dependency timefold-solver-spring-boot-starter --configuration runtimeClasspath
./gradlew :school-timetabling:dependencyInsight \
  --dependency timefold-solver-benchmark --configuration runtimeClasspath
```

관찰된 결과:

| component | resolved version | evidence |
|---|---:|---|
| `ai.timefold.solver:timefold-solver-core` | `2.6.0` | `dependencyInsight`가 `selected by rule`로 선택하고 starter/jackson의 transitive 요청도 `2.6.0`으로 수렴 |
| `ai.timefold.solver:timefold-solver-jackson` | `2.6.0` | `dependencies` graph에서 core `2.6.0`을 요청 |
| `ai.timefold.solver:timefold-solver-spring-boot-starter` | `2.6.0` | `dependencyInsight`가 `runtimeClasspath -> 2.6.0`으로 확인 |

모든 명령은 `BUILD SUCCESSFUL`로 종료했다. 이 결과는 현재 중앙 snapshot이
2.6.0을 관리한다는 뜻이지, catalog train 자체가 Maven artifact라는 뜻은
아니다. central BOM publish나 catalog tag는 이 issue 범위에서 수행하지 않는다.

중앙 dependencies 저장소의 governance 검사도 동일한 workspace에서 실행했다.

```bash

python3 scripts/sync-shared-versions.py --workspace .. --check --summary
python3 scripts/sync-dependabot-ignores.py --workspace .. --check --summary
```

세 명령 모두 exit status `0`이다. managed catalog는 aliases `188`, sub-BOM
`8`을 확인했고, shared-version 검사는 `Central catalog adoption is clean.`을
출력했으며, Dependabot ignore 검사는 drift 없이 종료했다.

### stale build helper 확인

`buildSrc/src/main/kotlin/Libs.kt`의 다음 선언은 검색 결과 선언부만 남아 있고
활성 build script에서 참조되지 않는다.

```text
Versions.timefold_solver = "1.32.0"
timefoldSolver(module, version)
timefold_solver_bom ... timefold_solver_webui
```

검증 명령:

```bash
rg -n "timefold_solver|timefoldSolver\\(" buildSrc 00-shared 01-quickstarts exposed
rg -n "timefold\\.solver\\.(core|jackson|spring\\.boot\\.starter|benchmark)" \
  gradle build.gradle.kts 00-shared 01-quickstarts exposed
```

첫 검색은 `Libs.kt` 선언부만, 두 번째 검색은 실제 `libs.timefold.solver.*`
사용부만 반환했다. 따라서 Task 1에서는 이 미사용 helper만 제거하고,
versionless catalog alias와 central BOM import는 유지한다.

## 채택 결정과 후속 검증

1. Timefold version source of truth는 중앙 `bluetape4k-dependencies` BOM으로
   유지한다.
2. workshop catalog는 module alias만 제공하고 local Timefold version을 다시
   도입하지 않는다.
3. 2.3/2.4 join/filter 수정과 2.5 stale tuple/filter 및 lifecycle race 수정은
   production stream을 추측해 고치지 않고 FULL_ASSERT 회귀 fixture로 먼저
   검증한다. RED가 재현될 때만 최소 production fix를 허용한다.
4. 2.5의 list-element declarative shadow 기능은 기존 shared 모듈의 독립 fixture로
   검증하고, 2.6 Neighborhoods iterator는 실제 사용 surface가 없으므로
   불필요한 custom move를 추가하지 않는다.
5. 다음 단계가 끝나면 이 ledger에 각 테스트 명령과 실제 통과 수를 덧붙인다.
   skip, disabled, static-only 결과는 통과 근거로 인정하지 않는다.

## Issue #54 Task 4 실행 결과

2026-09-14에 registry와 school controller lifecycle 테스트를 `--no-build-cache`로
실행했다.

```bash
./gradlew :school-timetabling:test \
  --tests '*TimetableJobRegistryTest' \
  --tests '*TimetableControllerTest' --no-build-cache
```

- registry: `6 passing` (best→final, best→failure, late callback, duplicate/blank
  ID, unknown callback, concurrent final/failure)
- controller: `3 passing` (SMALL/LARGE submit→NOT_SOLVING→final score, terminateEarly
  후 terminal score 수렴)
- 전체 targeted 결과: `9 passing`, `BUILD SUCCESSFUL`
- registry는 entry별 `ReentrantLock`과 `PENDING → COMPLETED|FAILED` 단일 전이로
  callback race를 차단한다. unknown callback은 무시하고, duplicate ID는 원래
  problem을 보존한다.
- controller는 Timefold 2.6 `withFinalBestSolutionEventConsumer`를 사용하고,
  동기 submit 실패도 registry에 FAILED로 남긴다. 요청 payload는 로그에 기록하지
  않으며, 결과 조회는 registry snapshot의 timetable을 복사해 status만 덧붙인다.
- registry map의 보존 기간/TTL은 기존 HTTP 계약에 명시되지 않아 별도 TODO로
  남겼다. Enterprise `analyze` 테스트는 기존처럼 disabled/N/A이다.
